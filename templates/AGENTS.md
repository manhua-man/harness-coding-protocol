> This file is **Facts (事)**: it answers "what is this repository?"  
> Store only verifiable project facts (layout, commands, ports, modules, APIs, commit conventions, etc.).

**Repo truth entry is fixed at root `AGENTS.md`, `CLAUDE.md`, and `steering/`. If the project has UI, brand, experience, or DX design constraints, use `DESIGN.md` for Design (设).**

## AI Entry Documentation (Division of Labor)

**事 (Facts) vs 法 (Protocol).** This file is **事** — *what this repository **is*** (structure, commands, ports, checkable conventions). Root **`CLAUDE.md`** is **法** — *how we **work** in this repository* (priorities, session protocol, collaboration habits). They are complementary entry docs, not alternative audiences. Read them **as the task requires** — not as a mandatory full pre-read before every edit. If only **`AGENTS.md`** is injected, read **`CLAUDE.md`** when protocol is needed; if only **`CLAUDE.md`** is injected, read **`AGENTS.md`** when facts are needed.

**Conceptual stack (layers, not install docs):**

```text
法 (CLAUDE.md)     — how to collaborate
  → 事 (AGENTS.md) — what the repository is
  → steering/      — scoped local overrides
  → docs/          — human long-form background (NOT an AI truth source)
```

**AI truth sources:** **`AGENTS.md` + `CLAUDE.md` only.** Topic-specific overrides live in **`steering/`** (or `.kiro/steering/` when the project uses that layout). **`docs/`** is human background — useful context, but if it conflicts with 事/法, fix the entry docs or the long doc; do not treat `docs/` as authority over `AGENTS.md` / `CLAUDE.md`.

**Decision tradeoffs** (testability vs readability vs …) live **only** in **`CLAUDE.md`** — not duplicated here.

| Character | File | Responsibility |
| --- | --- | --- |
| **Facts (事)** | **`AGENTS.md` (this file)** | Layout, commands, ports, modules, endpoints, commit/PR conventions; index `steering/` and `docs/` |
| **Protocol (法)** | `CLAUDE.md` | Decision priority, conflict resolution, risk-tiered RIPER Gate, collaboration habits and output requirements |
| **Design (设)** | `DESIGN.md` (on demand) | Product tone, visual tokens, layout, components, motion, copy, brand, and experience anti-patterns |

Body prose language must match the resolved locale in sibling `CLAUDE.md` (see **Language & Tone** there).

## Routing Not Recipes

This file routes; it does not teach step-by-step workflows.

- **Do** store verifiable facts, command entry points, ports, module ownership, and where to look next.
- **Do** state **targeted validation** by risk (see conditional **Targeted Validation** when evidence supports it).
- **Do** define **safe autonomous zones** when the repo has them — e.g. local disposable fixtures, no production access, rerun affected tests without per-step approval.
- **Do not** require reading the full doc tree, repo map, or unrelated skills before routine edits.
- **Do not** duplicate collaboration philosophy, approval policy, or blanket "always test everything" rules that belong in **`CLAUDE.md`** or a narrow skill.

## Tool and Documentation Routing

### AI Assistant Tool Index (dynamic)

> Generated by `/harness-init` **Agent Grounding** from existing stacks, AI tool traces, and repo evidence.
> Keep repository-native commands/scripts, repository-owned AI skills/commands, and recommended external/global tools separate.

#### Repository-native commands and scripts

List executable commands and scripts declared by manifests, CI, or authoritative ops docs. Route each task to the narrowest useful entry and name its evidence source.

#### Repository-owned AI skills and commands

List Skill, command, and workflow files that physically exist in this repository. If none exist, state that explicitly.

For each skill: keep the **description short and narrow** (when to use, not "use for anything touching X"); prefer a root skill file as a **router** to deeper docs/scripts; avoid overlapping "pick me" descriptions across skills.

When the repository has review, ops, or audit skills, index them in **three tiers** (locale-matched headings):

| Tier | When to list | Examples |
| --- | --- | --- |
| **Mandatory gates (fail-closed)** | Code change hits an irreversible or high-asset boundary | migrations, payments/auth, secrets |
| **User-invoked production ops** | Real production side effects; user names the task | deploy, patrol, gift codes, settlement |
| **On-demand tools** | Architecture/performance review; user or PR asks | module boundary, capacity, lint-style audits |

Do **not** flatten all skills into one table that reads like "run before every commit."

#### Recommended external / global tools

Include only tools explicitly selected by the user, routed by authoritative project docs, or intentionally preserved from the active IDE catalog. Label them as not bundled and availability-dependent; do not claim they are installed project dependencies.

_The agent inserts project-specific routing tables here in Phases 2–3 based on Grounding_Summary and read evidence._

### Documentation Routes

When a feature catalog exists or is generated, link its resolved index as the route to capability groups, implementation locations, validation results, and open issues. Detailed results live with feature owners; keep volatile status out of this file.

Link only long-form documents an unfamiliar Agent needs as an authority or navigation entry. Label each as current truth, target design, or historical material when that distinction matters. Omit everything else; do not copy roadmaps, iteration logs, historical validation snapshots, full design/release manuals, large test output, fast-changing runtime status, or sensitive credentials into this file.

Include scoped `steering/` links only when real overrides exist. Steering supplements root facts/protocol; it does not duplicate them.
