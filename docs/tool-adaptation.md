# 工具适配（Tool Adaptation）

工具适配解释某个具体的 harness、CLI、编辑器或自动化环境如何实现核心协议。它**不是**重新定义协议的地方。

稳定行为住在 `docs/run-contract.md`。本文档说明 adapter 在能力差异下如何保持那份行为。

## IDE init 命令（主 onboarding）

终端用户通过 AI IDE 内插件的 **`/harness-init`** 命令完成 onboarding，而不是终端 `harness` CLI。Adapter 把该命令映射为：

- **检测（Detection）** — 仓库扫描（技术栈、框架、AI 工具痕迹）
- **生成（Generation）** — 根级真值文件与工具镜像
- **应用（Apply）** — 在对话中获取确认后写入

参见 [docs/capabilities/](../capabilities/) 与 `README.md`。

## 适配原则

每个 adapter **必须**把本地能力映射到 run contract：

- 发现（Discovery）：搜索、文件阅读、符号查找、仓库元数据、项目文档。
- 计划（Planning）：harness 的用户可见更新或计划机制。
- 实现（Implementation）：当前可用的最安全编辑机制。
- 验证（Verification）：项目原生测试、检查、构建、浏览器核查或人工证据。
- 汇报（Reporting）：简洁终态响应，列出变更文件、验证结果、残留风险。

如果环境无法直接支持某个阶段，adapter **必须**记录降级路径。

## 能力矩阵

每个 bundle 或 adapter **应**声明：

- 文件读能力。
- 文件写/编辑能力。
- shell 或命令执行能力。
- 网络与浏览器能力。
- 测试/构建执行能力。
- 用户确认机制。
- 长任务或后台作业能力。
- 已知的沙箱、权限或平台限制。

矩阵要务实，不是装饰。它的目的是让维护者一眼判断 run contract 在该环境是否可被遵守。

## Adapter 必须遵守

MUST：

- 保留 run contract 的安全边界。
- 即使工具让某动作变得"轻松"，也保留用户确认规则。
- 偏好原生、结构化的操作，而不是脆弱的文本抓取。
- 诚实汇报缺失能力。
- 把环境特定指令排除在核心架构之外。

SHOULD：

- 能用 harness 原生编辑路径就不用 shell 小聪明。
- 项目原生验证优先于通用检查。
- 每个缺失能力提供一条清晰的备用方案。
- adapter 文档保持简短，并链接到权威契约。

AVOID：

- 因为"工具能跑 prompt"就声称兼容。
- 用礼貌语言遮盖降级行为。
- 在每个 adapter 内重复完整的协议规则。
- 给核心概念造一套 bundle 专属术语。

## 降级规则

某项能力缺失时，adapter 必须显式降级：

- 无 shell：用文件检视，并解释跳过的检查。
- 无浏览器：仅验证静态 UI 结构，并声明运行时 UI 行为未测。
- 无 patch 工具：使用最安全的编辑路径，避免大范围重写。
- 无文件系统读：向用户索取必要源内容，或停下。
- 无确认 UI：在需要确认的动作前停下。
- 无网络：只用本地资料，并说明外部事实未核查。

降级阶段后，adapter 不得伪称运行结果与未降级版等价。

## 与 Bundle 的关系

Bundle 是打包面。它可以包含：

- 工具特定安装说明。
- 能力映射。
- 本地命令示例。
- 环境特定注意事项。
- 帮助用户落地协议的最小代码片段。

Bundle **不得**包含：

- 第二份架构。
- 与核心冲突的 run contract。
- 弱化核心契约的独立安全规则。
- 喧宾夺主的长例。

如果某 bundle 需要新规则，请把规则提升到 `docs/run-contract.md`，或显式标注为"环境专属"。

## 评审对齐

评审指向更锋利的产品形态：adapter 应让协议可移植，而不是把项目变成"工具笔记堆"。一个好 adapter 是**朴素**的：映射能力、点名限制、然后让出舞台。
