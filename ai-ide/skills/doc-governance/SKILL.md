# Doc Governance（文档治理）

减少事实漂移、重复维护和过期内容，让读者能找到可信的当前契约。沿用调用方的任务范围与授权；审计请求本身不授权删除、实现修改或发布，也不为已经授权的工作增加逐块确认。

## 核心原则

- **单一权威来源**：同一契约只维护一份，其余引用。优先复用已有文档、schema 和生成参考，不为每个内部符号新建手册。
- **双轴正交分层**：按业务域或系统能力解决“去哪找”，按当前契约、历史经验、验证基线、未来规划解决“信不信”。复杂业务工程可按架构、功能、开发、运维分域；轻量管线可只按生命周期聚合。复用项目现有路径与语言，不强套目录名。
- **按任务决定阅读范围**：普通更新按变更及直接关联阅读；只有全盘审计才覆盖约定文档全集。文件数量本身不触发全量审计。
- **保留有价值的证据**：过期副本和过程稿先提炼有效契约再删除；有独立审计、决策或保留要求的历史记录明确标注状态。内容生产资产跟随所属项目，不混入系统文档。
- **诚实验证**：区分 mock、真实集成、推断与未运行。有版本意义的历史结果保留版本和范围，不把旧通过结果改写为当前全绿。

## Mode 1: Audit（只审不改）

### 机制一：分块全文盘点（--audit-corpus）

用户指定 `--audit-corpus`、要求全盘审计或明确要求存量收敛时，先列出约定范围的文档清单。按业务边界和上下文容量分块，逐篇阅读全文；不只看标题或搜索命中就宣称完成审计。记录已读、未读、排除范围及理由。

每块按三个维度给出文件、行号和代码证据：

| 维度 | 检查内容 |
| --- | --- |
| 冗余 | 重复定义、镜像副本、索引粘贴正文、已失效的过程计划 |
| 缺失 | 受众需要但未记录的契约、错误事实、断链、未说明的行为变化 |
| 待整合 | 分散的同主题知识、归档中仍有效的约束、混入交付文档的内部实现 |

可全盘审完再修改，也可在已授权范围内逐块收敛。涉及未授权删除、受众或契约含义不清时，先完成其余已授权工作，再说明需要决定的具体项。

### 机制二：代码与文档双向对账

**Doc → Code**：验证文档所称的路径、命令、配置、接口和行为是否存在且一致。

**Code → Doc**：以约定审计范围的实际代码清单为分母，结合受众和文档覆盖承诺找遗漏。以下是后端示例，其他技术栈按真实入口调整，不存在的类别跳过：

| 代码证据 | 文档核对点 |
| --- | --- |
| 注册模块和能力入口 | 业务能力与边界是否可找到权威说明 |
| Controller / 路由及鉴权 | 面向受众的路径、方法、权限、请求响应是否一致 |
| Entity / Migration / schema | 文档承诺覆盖的数据模型、关键约束与迁移状态；优先引用已有 schema |
| 错误码与 HTTP 状态映射 | 对外错误语义是否有说明或生成参考 |
| 环境变量与部署拓扑 | 配置要求、服务依赖、端口与运维步骤是否一致 |

逐项区分已覆盖、缺失、无需文档化、未核对。不要求手抄所有内部表、字段、函数或错误分支。源码存在不证明已经上线；生产或迁移状态需实际部署证据，没有证据则标为未确认。

同时检查冻结声明与后续变更、当前契约混入历史过程、数字或测试结论失去版本范围等漂移。输出按 P0/P1/P2 排序的证据与建议，不凭文档目录名判断真伪。

## Mode 2: Design（结构与交付边界）

优先微调现有结构。复杂工程可按业务域分目录，并在各文档中区分生命周期；轻量工程可用当前契约、经验和验证基线三类。空目录、单文件目录或新索引只有在确实改善查找时才引入。

### 机制四：交付目录与配置边界

仅在任务涉及客户端或外部团队文档时适用：

1. **按受众消除重复**：同内容副本优先合并；受众、访问权限或发布周期不同时可保留独立视图，共享契约从同一来源引用或生成。
2. **以调用契约为主**：说明接口、鉴权、参数、响应、错误码与调用时序。内部表、源码、锁实现通常留在内部文档，仅在接收方确需且获准共享时包含。
3. **按交付包检查链接**：需要离线交付时，本地引用必须能在包内解析。允许子目录及仍在包内的 `../`，也可链接接收方可访问的稳定外部资源，无需统一成 `./*.md`。
4. **区分内部整理与外发**：按 [update-docs Rule 5](../../commands/update-docs.md) 维护既有配置呈现。内部原稿保留不等于允许向新接收方复制真实凭据。外发材料按已确定的接收方与凭据策略处理，报告不回显真实值。

## Mode 3: Converge（执行已授权收敛）

### 机制三：生命周期转换与过程稿退役

- **完成的施工计划**：核实完成状态，将仍有效的架构约束、数据模型和运维步骤并入常态文档。更新引用后，删除已授权且无独立保留价值的过程稿；有审计或决策价值的标为历史记录。
- **未实施的草稿**：仍有价值的规划与当前实现明确隔离，已被替代且无保留价值的才删除。保留项目已有规划路径。
- **示例与伪代码**：先区分教学示例、伪代码、未来设计和当前实现。只有冒充当前实现且经核实不存在的片段才删除或修正；路径不存在本身不能证明虚构。有用示例保留并标注性质。
- **仍被依赖的归档**：先提取现行有效契约和排障知识、更新主线引用，再裁剪已授权范围内的废案，不能只因目录名含 archive 就删除。

收敛时每个概念确定一个权威来源，其余改为引用；索引保持简短。默认修正文档以匹配实际行为，发现代码缺陷只报告，除非当前任务也授权修复。AI 入口的变化路由至 `/revise-ai-docs` 或 steward，只有当前任务另有授权时才修改 `AGENTS.md` / `CLAUDE.md`。

### 机器证据清理

先统计截图、JSON、manifest 等的体量，区分当前验收基线与被后续结果取代的历史证据。只删除授权范围内、确认无独立价值的内容；未跟踪文件没有 Git 历史，不能以“Git 已保存”为由删除。不要修改单份 verdict、hash 或截图来制造通过结果。删除后同步引用；只有确实存在于 Git 历史的内容才可标“见 Git 历史”。

## 验证与交付

- 优先运行目标仓原生链接与布局检查，搜索被移动或删除的旧路径；历史记录中的引用按保留约定处理。
- 可选使用 [verify-docs-layout.mjs](scripts/verify-docs-layout.mjs)：`node <skill-dir>/scripts/verify-docs-layout.mjs <docs-dir>`。它粗查本地链接、要求 README 并拒绝 archive 等目录名；这些目录假设不适用于所有项目，不据此自动重组。脚本不验证锚点、外部访问权限或交付包边界。
- 按任务风险验证：纯 Markdown 修改检查链接、格式和相关契约；涉及可执行脚本、命令或实现时再扩大到相关测试或构建。运行 `git diff --check`，明确未运行的检查。
- 报告阅读覆盖、冗余/缺失/待整合矩阵、代码对账差异、合并/移动/删除/补齐项、验证结果及剩余歧义。没有结构变化时无需生成目录对比。
