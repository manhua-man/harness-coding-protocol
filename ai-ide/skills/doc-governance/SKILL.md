# Doc Governance (文档治理)

文档是负债，不是资产。每份文档都在向每次改动收税——税就是"同步它"的认知成本。
治理的目标不是"文档好看"，而是**让文档的税最低**：进场的人 5 分钟看懂现状，改动的人不用为文档付双重成本。

## 核心理念（先于一切方法）

1. **真值单源 (Single Source of Truth)**：可验证的事实（版本、路径、模型、命令、测试数）只写在一个文件里（如 AGENTS.md / FACTS.md），其他文档一律**指针引用，不复制**。复制 = 漂移，漂移 = 未来某天 AI 按错的数字干活。
2. **双轴正交分层 (Dual-Axis Orthogonal Model)**：
   - **空间维度（业务域与系统能力）**：解决"去哪找"。复杂系统按业务域或工程模块建立清晰目录骨架（如 `02-项目架构`、`03-功能模块`、`04-开发指南`、`05-运维部署` 或 `docs/features/`）。这是人类与 AI 最直观的认知入口。
   - **时间与状态维度（生命周期与契约真伪）**：解决"信不信"。严格隔离"活的真理契约"、"实战经验沉淀"（06-复盘与沉淀）、"验证基线"（05-测试与基准）与"未来演进"（08-迭代方向）。严禁把临时排查过程、过期方案混入活的业务真理中。
   - **与 documentation-architecture 协同**：业务能力目录（`03-功能模块/` 或 `docs/features/`）由 `documentation-architecture` 依据代码实证提取维护；`doc-governance` 负责全域生命周期审计、坏链巡检与拓扑收敛。
3. **项目内容与系统文档分离**：`docs/` 只放系统/管线文档。项目生产内容（剧本、分镜、对白、系列设定）归 `projects/<项目>/docs/`，跟着项目走，不进系统文档空间。
4. **死文档直接删除，不建 archive**：git 历史就是存档。只有极少数有独立审计/决策价值的才保留，其余 `git rm` 干净利落。
5. **诚实标注，禁止膨胀文案**：mock 测试就是 mock，写 `UNIT_ONLY`；冻结就是冻结，写 `FROZEN` 之后不许再改。文档吹的每一句牛，都会变成后人踩的坑。

## 治理流程（Audit → Design → Converge）

### Mode 1: Audit（只审不改）

**A. 找事实漂移**（最优先，P0）：
- 文档声称的数字 vs 实测：跑测试、跑 `git log`、数文件，**拿证据对质文档**。
- 例：AGENTS.md 写 "45/45 全通"，实测 50 个 —— 多源事实已经各说各话。
- 例：BUILD_INFO 写 "50_PASSED_REAL_INTEGRATION"，实测 0.76s 的 mock 测试 —— 膨胀文案。

**B. 找幽灵引用**：
- grep 文档/CLI 里提到的文件名，`ls` 看是否真实存在。
- 例：CLI choices 接受 `fast_preview`，但 `pipelines/` 下根本没有这个文件 —— 幽灵选项。

**C. 找冻结失效**：
- 声明 "FROZEN" 后 git log 是否还有功能性提交？有 = 冻结是装饰，不是状态。

**D. 找重复与混层**：
- 同名/近名文档并存（如 ARCHITECTURE.md vs system_architecture.md）—— 确认是"当前实现 vs 长期愿景"还是纯重复，重复就合并。
- 当前真理文档里混着执行历史/日期日志 —— 拆出去。
- 过程记录（迁移说明、施工过程、原始参考）躺在主目录 —— 标记为死文档。

输出：审计报告（P0/P1/P2 分级 + 每项证据：文件:行号）。

### Mode 2: Design（设计目标结构）

针对项目规模，提供两套经过工程验证的标准目录模型：

#### 形态 A：大型/复杂工程体系（业务域驱动 + 生命周期守卫）
适合复杂客户端、服务端、完整游戏与业务系统。空间上按系统域分拆，时间上严格执行生命周期隔离：

```text
docs/
├── README.md           # 导航总控：系统大图 + 目录路由
├── 02-项目架构/        # 架构真理（系统拓扑、通信协议、管线标准）
├── 03-功能模块/        # 业务/能力真理（由 documentation-architecture 提取维护的 Feature 矩阵）
├── 04-开发指南/        # 工程真理（环境搭建、编码规范、调试避坑）
├── 05-测试与基准/      # 验证基线（实测报告、性能基准数据、自动化测试留痕）
├── 06-复盘与沉淀/      # 经验沉淀（实战踩坑、全景复盘、教训总结）
└── 08-迭代方向/        # 未来演进（路线图、下一阶段技术选型）
```

#### 形态 B：轻量/管线型工程（纯生命周期驱动）
适合单脚本、算法管线、轻量工具：

```text
docs/
├── README.md           # 导航索引：组织理念 + 使用约定 + 目录路由
├── 01-<当前真理>/       # 活的契约：架构、规范、标准、路线图（现在是什么）
├── 02-<经验沉淀>/       # 实战教训、学习笔记（我们学到什么）
└── 03-<验证基线>/       # 测试报告、上游快照、审计记录（我们验证过什么）
```

约束：
- **目录只建"有真实边界"的**：单份文档不建目录；空目录/单文件目录拍平。
- **README 只导航不复制内容**：路由读者到文件，不重复文件内容。
- **语言/命名跟仓库走**：仓库是中文就中文，别硬套英文编号。
- **理念与结构相称**：小型工具采用形态 B 即可，避免过度分层；中大型业务工程推荐采用形态 A，使业务模块与生命周期职责各自清晰。

### Mode 3: Converge（执行收敛）

1. **改代码**：删幽灵选项/特判（CLI choices、registry 别名），先让代码和现实一致。
2. **收敛真值**：选定一个真值文件，其余文档改指针引用；测试数这类会漂移的数字改成"pytest 全绿"这类不再漂移的表述。
3. **合并重复**：确认重复后合并成一份，`git rm` 另一份。
4. **删死文档**：`git rm` 过程记录，不留 archive 目录（git 历史就是 archive）。
5. **分离项目内容**：项目文档 `git mv` 到 `projects/<项目>/docs/`。
6. **同步所有引用**：README、AGENTS.md、CLAUDE.md 的路径/数字一起改，不留断链。

## 机器证据清理（screenshots / JSON / 截图）

机器证据（截图、JSON、manifest）是文档里最重的部分，也是最容易失控的。治理时单独处理：

1. **先算账**：`du -sh` + `find | wc -l`，找出体量异常的目录（如 17000 文件 / 400MB 的一次性验收截图）。
2. **区分"当前验收基线" vs "一次性历史证据"**：
   - 当前验收基线（如正式 R3 验收的 pairs/）→ **保留**，有独立审计价值。
   - 一次性历史证据（如某次 07-17 重检，结论已被后续正式验收取代）→ **可删**，git 历史已保留。
3. **删除方式**：
   - 被 git 跟踪的 → `git rm -r`（历史保留）。
   - 未跟踪的（在 .gitignore / 从未 add）→ `rm -rf` 物理删除，不占 git。
   - 注意：`git rm` 只删跟踪文件，未跟踪的还在磁盘，要 `rm -rf` 补刀。
4. **同步引用**：被删目录若被文档引用，改引用为"该目录已清理归档，原始证据见 git 历史"，不留断链。
5. **红线不变**：清理是删整目录，绝不手改单个 verdict/hash/截图内容。

## 对"已治理仓库"的处理（重要经验）

有些仓库的 docs 已经按生命周期组织好了（README 按问题路由、五类分明、机器证据路径稳定）。此时：
- **不要硬套新结构**——它已经符合理念，强行重组是负优化。
- Audit 的产出应该是"确认它符合 + 指出少量边角问题"，而不是"推翻重来"。
- 判断标准：README 是否按问题路由？当前真值是否与已执行工作分开？机器证据是否生成器驱动？诚实标注是否到位？—— 四项都满足 = 已治理，只做微调。

## 试炼案例：sophon-clone（2026-08-21）

- 该项目 docs 已是生命周期治理样板：README 按问题路由、五类分明、机器证据生成器驱动、诚实标注（"这不表示动态内容逐像素一致、Sophon figure parity"）。
- 发现并处理：`compare-recheck-20260717-same-session/`（17005 文件 402MB）和 `visual-parity-recheck-20260717-1440/`（87 文件）是一次性历史验收，被正式 R3 取代，git 有记录 → 删除并同步引用。screenshots 从 21949 文件 716MB 降到 4857 文件 312MB。
- 边角问题：顶层 7 份"当前真值"md 平铺在 docs/ 根，与 README 混在一起——但 README 的"当前真值"表格已声明边界，实际效果可接受，不强拆。

## 验证清单（Converge 后必跑）

- [ ] 目录架构与断链体检：运行 `node ai-ide/skills/doc-governance/scripts/verify-docs-layout.mjs docs` 全绿通过
- [ ] `grep` 幽灵引用：grep 被删文件名，应无残留（审计报告本身除外）
- [ ] 断链检查：grep 文档里引用的相对路径，逐个确认存在
- [ ] 测试回归：`pytest` 全绿（或项目原生 check 命令）
- [ ] `git diff --check` 无空白错误
- [ ] 被删文件的链接已清理或改为指针
- [ ] 真值文件里没有过时数字
- [ ] 机器证据：被删截图目录的引用已改"见 git 历史"，未跟踪的大目录已 `rm -rf`

## 常见陷阱

1. **把"归档"当默认**：`mkdir archive/` 然后移文件 —— 错。默认是 `git rm`，archive 只在有独立审计价值时用。
2. **混淆生命周期与混层存放**：把执行过程记录、临时草案、过期测试与业务真理混在同一个业务模块目录下 —— 错。业务模块下只放活的系统契约，过程与复盘请归入独立的经验（06-复盘沉淀）或基线（05-测试基准）目录。
3. **项目内容混进 docs/**：剧本、分镜、设定进 `docs/` —— 错。归 `projects/<项目>/docs/`。
4. **README 复制内容**：索引页把架构/命令表又抄一遍 —— 错。只路由，不复制。
5. **测试数写死**：文档写"45/45"——错。写"pytest 全绿"，数字必然漂移。
6. **吹牛**：mock 写 REAL_INTEGRATION、FROZEN 后又提交 —— 错。诚实标注，否则后人是按你的牛在决策。

## 报告格式（交付物）

- 治理前后结构对比（before/after tree）
- 每类操作计数：合并 X、移动 Y、删除 Z、保留 W
- 验证结果：测试、链接、grep 残留
- 遗留项：未解决的歧义、后续候选
